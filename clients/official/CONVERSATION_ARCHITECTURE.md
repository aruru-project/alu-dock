# Conversation UI ownership

The official client keeps one Protocol V2 conversation state and the existing projection/live reducer path. Start with the [official client map](../../docs/agent_maps/official-client.md) for user-entry ownership, file/platform boundaries and focused validation. The [client design principles](../../docs/client-design-principles.md) are maintained there as one authoritative text.

- `src/lib/conversationContent.ts` owns the one disposable display projection: native record chunks, checkpoint handoff, live delta folding, frame scheduling, streaming markers and layout notifications. It has no history scan, descriptor cursor, body request queue, retry policy or whole-page hydration barrier. History records and `createLiveConversationProjector` remain the only rendering path. It retains previous rendered objects while native membership is applied in place to the single records array; a small ID/order set marks that display transaction, not a second records snapshot. Native read facts establish text/tool fold boundaries before post-cut events arrive. A rebuilt binding supplies its canonical post-cut replay before the seed end marker, so an older checkpoint never attempts to split an already folded `AB` using only its first sequence. The one live projector is rebuilt at the end; there is no approximate second renderer. Initial empty-view seeds can paint incrementally. It never guesses a persistent entry ID from a live message ID or from text.
- `src/lib/conversationSession.ts` is the conversation region's local backend interface. Its inputs are the selected connection/Work/Host facts and native content emissions, not App refresh/reset/recovery callbacks. It sends `earlier`, `interest` and `retry` intents to `read_conversation_content`; native content tokens fence responses independently of selection generation. Read errors/loading are display copies of native facts. The conversation store (`src/stores/conversation.ts`) composes this interface, the projector and viewport behind the `ConversationSink` it attaches to the observation store; `src/stores/observation.ts` alone routes the shared observation lane.
- `src/lib/conversationViewport.ts` owns follow intent, actual-bottom geometry, row/text anchors, layout observation, and every application-authored conversation scroll write. Content and media owners call `layoutChanged()` rather than scrolling directly. `scrollToBottom()` is the explicit reliable end action.
- `src/components/ConversationView.vue` groups stable rows into turns; `ConversationTurnSummary.vue` renders each turn's summary line, `ConversationRow.vue` and `ConversationProcessPart.vue` own row/part rendering. Raw assistant text is assembled on request, and tool detail serialization happens only in its own expanded part. The view does not load, project, or scroll content; expanding or collapsing a turn goes through the store's `holdReadingPosition` so the viewport keeps the reader's row in place. Its visibility observer emits source entry IDs supplied by the history projector (including tool-group membership), never parsed row IDs; the native reader only queues demanded incomplete bodies, prioritizing current visible entries. Already-running body reads finish rather than being repeatedly cancelled.
- `src/App.vue` lays out the topbar, conversation, input/Queue, sidebar and dialogs and starts the page-wide listeners in order. It owns no observation reducer, operation claim, upload/image orchestration, Host form or platform policy. The stores below live for the page lifetime; rendering an expanded editor or a covering dialog does not create another editor or operation owner.
- Each conversation component styles itself in its own `<style scoped>` block (rows, process parts, inline images, reading controls and their responsive rules). `src/styles/conversation.css` holds what several of them share: the `.alu-output` scroller, message text, and Markdown rendered through `v-html`.

## Turns

A turn is one Agent run. The flat `ConversationItem[]` stays the only display structure: both projectors emit a `turn` item (status, `startedAt`/`endedAt`, error) and stamp every item of that run with its `turnId`; `conversationSections` in `conversationPresentation.ts` is the pure render-layer grouping and owns no state. The live projector opens a turn at `run.started` and settles it at `run.settled`; a steer message stays inside. A read that finds the run already in progress (`execution === 'running'` with no `run.started` in its replay, or a replay whose first run boundary is a `run.settled`) opens a *continuation* turn, which the render layer merges into the last history turn; a `message.submitted` with `delivery: 'prompt'` seen without `run.started` makes it an exact turn instead. History has no run boundaries: a user message opens a turn that ends at the last message record before the next user message; summaries, shell records and extension messages after that last message stand between turns. History duration is the record-timestamp span; status comes from the last assistant record's `stopReason`/`error`, and only the last history turn can be reported as unfinished. The run outcome lives in the turn item, so neither projector emits a separate settlement notice, and the assistant error that ended a run is not repeated below its summary. The local send placeholder is a running turn item that the next structural publish replaces. A recovery read that says the Work is not running settles an open live turn from `lastRun`/`lastError`; one that says running with no open turn opens a continuation.

A user shell command (Pi `!` / `!!`, card #336) is a `shell` item, never part of a turn: the live projector builds it from `bash.started` / `bash.output` / `bash.completed` (keyed by `operationId`, output kept as a bounded tail), leaves it out of the running turn and untouched by `run.settled`, and the history projector builds the same item from a `bash_execution` record. `ShellRunRow.vue` renders both; `shellRunQuote` is the text 「发给 agent」 appends to the draft (`input.appendShellQuote`), shaped like Pi's own model-context text so a truncated output points at the full file path instead of pretending to be complete. `WorkspaceCommandArea.vue` in the workspace panel only lists these items and submits `run_shell_command` / `abort_shell_commands` through `work-actions`; closing the panel changes nothing about a running command.

Collapsed turns still show the reader's own messages, images, warnings/errors and the final reply (`partVisibleWhenCollapsed`); everything else is process. The final reply is the turn's last Agent message row: every text block and notice in it stays, only its thinking and tool calls fold, and the row is rendered even while an incomplete preview has no text yet, so its reading interest still reaches the native reader. A running turn is open by default and folds when it settles; a choice the reader made by clicking the summary line always wins, and a turn without one stays open on settlement only if the reader has scrolled away from the bottom (`reconcileTurnOverrides`). The view keeps these overrides only for its own lifetime and carries one across the live→history id change at the same position, including when settlement and that handoff land in the same update. A saved reading position (F5) that points into a collapsed turn's process opens that turn before the viewport looks for its entry (`turnHidingAnchor`). A settled turn without an end time shows no duration. There is no global detail/compact mode.

Before a live reply becomes completed Markdown, content requests a text-preserving snapshot from the viewport. The viewport uses a native caret/range and the same exact text occurrence within that part; unchanged nodes take the fast path. The projector reports existing affected part identities; tail appends and changes below the reading position bypass anchor capture. Existing anchor elements are restored directly; a replaced part is looked up by identity. Native image part IDs include their contentRef as well as occurrence context, so successive different images in the same tool content slot have distinct component and anchor identities. Settlement includes every currently streaming part that is about to change presentation, even when there are no tools. Text capture happens at presentation transition, not on every delta. If caret capture or exact matching is unavailable, restoration falls back to the part-level anchor rather than interpreting or rewriting message content. Automatic layout restoration never uses the explicit forced-end action, and a scroll event with no downward movement cannot resume near-bottom following.

Debug content/history from the methods returned by `useConversationContent`; debug reading/follow behavior from the methods returned by `useConversationViewport`. The development browser preview answers native calls from `src/preview/native.ts` (Host, Works, panels; `?preview=onboarding` / `?preview=offline`) and shows no conversation; a production build contains none of it. Conversation validation data is supplied by a `verify:preview --fixture` plugin, not by production hooks.

## Page regions and local API calls

Each region component reads the Pinia stores it needs (structure rules: client [AGENTS](AGENTS.md#前端结构)). Stores depend in one direction: `app` / `surfaces` / `platform` ← `observation` ← `host`, `conversation`, `control-panel`, `work-actions`, `attachments`, `operations`, `deliveries` ← `input`; within the middle group `attachments` uses `host`, `operations` uses `attachments`, and `work-actions` uses `host`. A lower store reports to a higher one through a subscription the higher store registers (`observation.attachDisplay`, `onConfigChanged`, `onCompactionSettled`, `onReplaced`; `attachments.onError`; `operations.setFailurePresenter`), never by importing it. There is no method dispatcher and no second native registry:

| Store / region | Inputs and callers | Owned result |
| --- | --- | --- |
| `stores/observation.ts` | One `aludock://observation` listener; selected native Work facts; the attached `ConversationSink`; window focus and the Windows away period | Binding/revision fence, control reducer, read-only Queue/status, frame ACK, native load/detach intents and when observation pauses or resumes |
| `stores/operations.ts` | One `aludock://operation` listener plus `pending_operations` initialization | Existing store projection, original-revision claims and acknowledgement; retained returned/unseen-failure results (a lost reply is one of these failures) |
| `stores/app.ts` | `captureOperationTarget(context, workId)` for controls; `captureOperation(context, workId, fileIds?)` for editor handoffs; `captureHostOperation(context)` for Host actions | Frozen dispatch targets; durable text/attachment capture only for editor-bearing actions; per-Work restored-image counts; native-operation Map is read-only to consumers |
| `stores/input.ts` / `InputRegion.vue` | Read-only native status/Queue and action gates, attachment store, page surface intents | One compact/expanded composer, local keyboard/suggestions and desktop shortcuts, submit/Queue surface feedback and visible failure handoff |
| `stores/conversation.ts` / `ConversationRegion.vue` | The observation store's display sink; standard image fileId | Existing projector/session/viewport, display image resources and tool expansion; only explicit latest/activity intents come from outside |
| `stores/surfaces.ts` / `PageDialogs.vue` | UI open/close/confirm intents, editor expanded/composition state and Extension focus ownership | Surface elements, focus/back/Escape/wheel, text/image preview state; no native facts or operation ledger |
| `stores/control-panel.ts`, `ControlCenter.vue`, `SessionManager.vue`, `command-console.ts` | Typed local queries/mutations and the accepted config events | Panel query results (models, tools, resources, settings), commands, Session/Tree controls and trust continuation; mutation await results do not claim drafts or publish a second global result |
| `stores/work-actions.ts`, `WorkSidebar.vue` | Typed Work APIs, local pending gates and page intents | Work buttons/compaction/query feedback fenced to its captured Host/selection/Work (and Session for session actions), Machine/list grouping and current initiating create selection |
| `stores/attachments.ts` | Native pick/stage/start/cancel APIs, revisioned read-only `attachment_snapshot` and progress notifications | Current pending selection; receipt-to-editor save, target applicability and disposable native-handle preview URLs; core `attachment_jobs.rs` owns source/job/progress/terminal facts |
| `stores/deliveries.ts`, `stores/host.ts`, `stores/platform.ts` | Existing typed local APIs and their scoped listeners | Downloads/history, Host/pairing forms, and App settings/desktop shell respectively |

Stores return plain refs and actions; components take them with `storeToRefs`. A view's own form models and DOM refs stay in the component unless a store action needs the element (surface frames, the editor textareas, the conversation scroller, the Dock Tools trigger). There is no runtime façade or copied DTO. Page focus/event handlers and action bookkeeping with no outside caller remain private. The unused local `setExtensionToolsExpanded` bridge and Tauri wrapper are removed; the core/Host tools-expanded capability is unchanged.

Observation keeps only control facts (`instance`, cursor, Queue) separate from the disposable content bootstrap metadata. Input never reads or writes `conversationContent.queue`. A current recovery Read also settles an open running turn when execution has ended, without waiting for history handoff or another settlement event; older Reads cannot overwrite newer activity. Running facts do not add a second turn to one already open. A dequeue receipt removes only its returned IDs from the current matching control Queue; it does not move the control sequence past unseen display events. `queue.cleared` and later `message.queued` can arrive on either side of that receipt. Accepted ordinary Work events use the Extension live reducer, not a fresh authoritative Extension snapshot on every metrics/pending event; this preserves local answers and per-tool expansion.

The TypeScript mutation bridge requires an explicit frozen `OperationTarget`, editor-bearing `OperationContext`, or `HostOperationContext`. Target-only capture checks the same connection/Work/epoch/runtime scope without flushing editor storage; these controls pass `operationEditor: null` to the existing native API. Send and Session editor handoffs additionally require a successful revision flush before dispatch. Queue retrieval is target-only: on success, it inserts the returned messages in their given order before the editor's then-current text and adds all returned attachments to the existing selection. It takes no editor snapshot and needs no second append action. Abort is one target-only `abort_run` (`command.abort_restore_queue`): the Host stops the run and returns every not-yet-started Queue item in the same step, and the result is inserted exactly like Queue retrieval. Items already handed to the Agent are reported, never a precondition. Only when an older Host explicitly lacks `run.abort-restore-queue.v1` does core fall back to dequeue then abort. The bridge never looks up a module-global editor provider. The Session trust continuation keeps its original editor capture. Queries still accept ordinary `SessionContext`/`ConnectionContext`. Which Works exist comes only from the Host's list (bootstrap and list reads); the current Work's state comes from its read and the live events that continue from that read. Operation results and query results report only their own operation: the Work copy they carry is never merged, because it can be older than events already shown or outlive a stopped Work. The shared acceptance entry (`app.applyWorkSnapshot`) drops a state for a Work the list does not have, and orders list reads against the current Work's reads and live events by runtime generation and then the Host journal position in `eventCursor`, never by `updatedAt` or `ownerHostEpoch`. Create, Continue and Stop concern a Work that is not being followed, so the screen that started them places the page from the Host's direct answer: a created Work is added and opened, a continued Work becomes active and is followed, a stopped Work leaves the list and its page at once. Each then reads the list in the background. Only the still-current creating panel chooses its newly created Work.

Button promises report local pending/error, completion/close and trust continuation. Native operation delivery alone applies editor results. Send cleanup and Session editor replacements check the original editing revision; Queue insertion uses the current editor without that check. Explicit Session returned-text append is protected against a double click; unclaimed Session text remains natively available. Local application and in-flight acknowledgement are separate: the existing applied-ID set protects current-view editor effects, while a pending promise deduplicates acknowledgement. Returned draft/Queue/explicit append use the store's candidate → durable save → publication transaction; failure leaves the editor revision and native result untouched and offers retry. Only applied-but-unconfirmed returned operation IDs are saved in that same editor transaction. Rebuilding the view retries acknowledgement, not append; successful confirmation removes the marker, and native snapshot reconciliation removes markers no longer retained by the current App run. This is not a permanent operation ledger. A successful send whose editor cleanup cannot be saved likewise retains its native result and retries cleanup, not sending. A lost reply (core `unknown`) is never replayed and is presented exactly like a failure: the initiating control says once that the connection dropped and no result arrived, or, when it is no longer on screen, the Work/list result entry does until acknowledged. There is no refresh-to-confirm action and it disables nothing; whether it took effect is read from the conversation and Work state. A failed send is acknowledged only after the input owner shows it for a frame and rechecks scope, visibility and covering surfaces; otherwise it stays in its Work/list result entry.

Uploads stay with their original Work while the user switches Works or requests Stop. There is no page-wide transition-busy condition: Work controls and sends track their own pending targets. The command panel reads only the section being opened; static operations remain available while its command catalog loads, and resource/tool sections report their own loading or errors independently. Extension reply and refresh completions update only the initiating interaction, not the next question's answer.

Work action feedback captures its initiating connection, selection generation, Host epoch and Work plus the local selection revision before awaits/confirmations. Abort and compaction also fence runtime/Session. Only matching current-surface feedback is exposed; a target switch hides old feedback, and a late catch cannot write it into the new page. Stop/Reopen/Forget feedback uses the Work lifecycle scope so the action's own lifecycle change does not masquerade as another Work. Native unconsumed results remain separately available.

Surface element registration is per actual page dialog, so closing a confirmation does not erase the element of the underlying dialog. Confirmation cancellation restores its trigger; ordinary modal dismissal prioritizes an active Extension answer. Compact/expanded are still the same `composer.ts` owner and share draft, selection and composition. Conversation read/Follow readiness and unrelated control operations do not gate Work-targeted sends, the textarea's existence, editability or focus. Sending goes directly to the specified Work without a pre-send conversation read; captured editor revisions and attachment ownership still govern cleanup and file safety. Local commands and Stop retain their independent action semantics.

Upload facts now live in the reusable core `attachment_jobs.rs` for the current native run. An owned task retains its source through active readers and saves progress/receipt/failure/unknown before notification. Tauri assembles platform imports, scoped start/query/cancel/remove and notifications; Vue rebinds via read-only revisioned snapshots, never by re-uploading. Current pending job references have independent selection revisions: successful receipt replacement and removal publish only after the same local JSON save succeeds, later typing does not revoke them. Imports rejected before selection acceptance are discarded rather than exposed as upload history. A confirmed direct or Queue submit retires only upload jobs captured before that send; later selections, failures and unknown submits are not consumed. No second attachment tray is derived from unselected native jobs. Permanent uploaded fileId receipts remain sendable without a current-run source/job, subject to their existing Host/Work/Machine/epoch/runtime scope and Host acceptance; pending selections still require their native job. Sources are immutable private imports in the same SessionContent RunCache: picker copies and clipboard/Android readers finish with an RAII file lease, shared by uploads and preview MediaHandles. Unaccepted imports are not retained by the display index. Native receipt completion checks the imported SHA/length/MIME before registering its authority/Machine/fileId alias; Vue does not supply a second file truth. Published images use the same media owner and file.read sink; saves copy the opaque handle through the existing platform staging/commit. Reading intent is persisted by the viewport, separately from native file/operation facts. Resource working-set boundaries are documented in the official client map. Reopen's project-trust confirmation UI was already absent at this stage's baseline (a write-only continuation had no caller). That dead UI state is removed; the real bridge and native trust refusal remain intact, and the known failure remains available in OperationResults. A Reopen trust-confirmation UI is still unimplemented (#304 backlog), not an implicit trust decision.

Focused evidence uses the actual App and independently mounted `InputRegion` with the real Pinia stores and a native IPC fixture: Queue 1/2/3 insertion before the current draft with all attachments, receipt/event reorder with a new intervening ID, display events, acknowledgement failure/retry after successful insertion or send, action failure before/after switching Work, late send after editing/switching Work, native local read failure, ordinary command modal/Extension answer retention, two page-level IME-aware Escape layers, confirmation cancellation and focus return. The independent input mount has no App/Layout or ConversationView DOM, but still constructs the real conversation owner for the fixed observation sink; it does not prove display-owner-free startup. Session/NewWork gates use the real app store rather than a fake editor provider. These are component/native-boundary checks, not a real Tauri WebView, OS IME or device acceptance.

The review's existing baseline notes remain outside this repair: nested Android Back history, late download/Host-form feedback, late platform/Extension listener registration cleanup, and Extension's own IME Escape handler. Page-level Escape and ordinary confirmation focus evidence must not be described as proving those four boundaries.

## Recovery, editing and focus

Ordinary Follow is same-domain strictly increasing, not consecutive: Host-private controller events keep their journal numbers. Core `FollowStream` validates that contract; the existing Vue reducer still owns its disposable projection.

`crates/aludock-client-core/src/session_content.rs` is the App-lifetime canonical holding point for the accepted read header, ordered history membership, immutable in-memory record versions, descriptor/read-task state, raw accepted tail, target, cursor and local commit revision. `session_records.rs` encodes each accepted body once as an immutable `Arc<str>` JSON value. Current membership, checkpoints, the commit segments and actual readers share that body; superseded or unpublished versions release with their last reference. Body encoding runs outside the content lock; larger preparation remains on blocking workers rather than the async continuation thread. Host-returned history can be displayed without per-record directory creation, permissions, file sync, SHA hashing or readback. There is no body disk cache, background writer or second content owner. Media files still use the existing RunCache. `claim` revokes a previous reader before new work can publish. `bind` pins a read header, a shared record index, the commit position and a coalescing revision notification under the content lock; it does not copy or decode bodies there. `session_content/binding.rs` chunks the shared bodies outside that lock. A rebuilt view receives complete retained record versions directly, not a preview followed by a mandatory network hydration. The current namespace includes saved connection authority (the configured endpoint for `local`), Work and Host epoch; runtime/Session are accepted content-domain facts, never inferred from a WebView subscription. `replace` compares authority, Work, runtime and the authoritative result eventCursor before accepting a receipt. The freshness check, owner revocation, target commit and revision publication are one critical section. Same-runtime Tree navigation requires a strictly newer Host journal position and the same Session; equal positions are event-before-reply/duplicate receipts, not another clear. `session.navigated` and `session.replaced` use the same content commitment, while their operation-specific returned text remains separately claimable. Accepted replacement retires old active/Queue ownership before any subsequent read or Extension cleanup. An accepted recovery Read first checks owner, Host/Work and cursor order, then commits a minimal priority replacement if runtime or Session identity changed, before body encoding. The new Read then installs its own content. A priority replacement can bypass an unread old tail; neither target acceptance nor replay requires disk recovery. An ordinary same-domain Read remains a forward checkpoint and does not clear the display.

`observation.rs` owns read/follow continuation and retries, not rendering. It resumes from the accepted cursor after transport failure, reads when the cursor/domain requires it, and keeps paused, connecting, connected, disconnected, identity and Host-change states distinct. Canonical commits are retained in the existing in-memory `session_journal.rs` segments rather than triggering threshold-driven network reads. Each segment stores shared commit references with their replay byte sizes; append preparation and source-event cloning/encoding happen outside its short lock. Readers copy only a bounded batch of references under that lock, then clone source events outside it. Checkpoints link successor segments, so pinned readers continue across rotation while publication proceeds. Old segments survive only while referenced by a checkpoint or reader, without a disk journal or file-lease side map. A settled run or `compaction.completed` can request a background authority checkpoint; failure does not interrupt a valid Follow, and a checkpoint older than the accepted cursor cannot publish. Observation facts (target, Queue, Extension and remote cut) are delivered before post-cut Follow, separately from content retirement. `session_content_reader.rs` coalesces the latest pending content checkpoint. If last-200 and the retained history do not overlap, it reads `session.history(beforeEntryId)` back to the retained lower boundary (or the actual beginning of the current branch). Ordinary append may change numeric history revision; stable anchored intervals, source identity and the fixed accepted upper cut are the proof, not equality of that global counter. A lower boundary changed by a concurrent earlier-page request must be re-proved. Until then the old index and raw tail remain rebindable. The proven interval preserves complete versions and covers records previously present only in raw events. Missing previously retained members prove a branch change and reuse the existing priority replacement cut, including its post-cut raw replay; an unread old body cannot delay that replacement. A stale Read owned by the current observation is not owner supersession: if a newer checkpoint is already accepted, Follow continues from its cursor; if a replacement still has no read, the foreground keeps read_required and reads again. Only a revoked owner ends that continuation. Observation, not catalog refresh, is the recovery prerequisite. Windows-away/Android background detach pauses observation without deleting its holding point; network-route reselection reconnects natively.

Tauri retains the display relay handle and projects the existing canonical DTOs. `aludock://observation` carries connection/selection/Work/subscription binding plus a local revision and a header snapshot or bounded batch. `read` initializes a target; `facts` applies an accepted same-domain read's non-content facts without clearing the conversation; `content` carries record chunks, checkpoint begin/end and local read states. Session/branch replacement still uses the priority control path. The header has a native content token and earlier-availability fact, not all retained records or bodies. A newer header with the same native content token updates only control facts before entering the retained seed/handoff; its empty records field does not clear already displayed bodies. Changed tokens still retire the prior branch immediately, even when runtime and Session IDs are unchanged. Current earlier-availability comes from the header/State, not the old checkpoint window's historyTruncated flag at End; an initial read still supplies the boundary when no later fact is present.

`SessionBinding::next_batch` uses the existing 256 KiB / 64-commit budget for both record seeds and journal replay. Shared record bodies are sliced at UTF-8 boundaries into at most 32 KiB chunks. Vue assembles only the current record. The larger-indivisible-source-event exception remains for existing Dock source events; a completed body cannot use it to create a giant IPC record. Metadata transactions publish an earlier page or coverage handoff together; this is not a body-completion barrier. Each independently completed body is committed/published immediately. Member installation and commit publication share the content admission lock.

Local content revision and remote event sequence are different facts. A pinned native `ReplayEvent` carries its content token and is delivered before the binding seed end at its captured waterline. It rebuilds the current display replay log independently of whether the control reducer has already seen that remote sequence; the old projector remains visible until the seed closes. Control facts still use the existing remote-sequence reducer. This also handles a priority header whose local revision is newer than the post-cut commit position. Ordinary events keep the existing revision fence. Record seed chunks may share their header revision and do not get discarded merely because no new remote event occurred. No live/history identity is fabricated. An empty view shows a local “reading conversation” state while a large retained record is being seeded; seed errors stop that waiting state without resetting the composer.

One ordinary delivery remains in flight until Vue's frame ACK (`acknowledge_conversation_follow`, binding and delivery ID only). A committed replacement may preempt one obsolete data delivery; subsequent replacements coalesce until that control checkpoint is acknowledged. Ordinary same-domain lag or checkpoints cannot take this path. There is no unbounded IPC backlog or extra all-body snapshot. Existing same-target catalog/connection behavior, editing continuity, local operation results and Extension input ownership remain unchanged. The bottom-bar intervention details remain user-opened; content failures do not open modals or move editor focus.

Read, initial Follow replay and live events share terminal admission. Confirmed terminal Work facts (including not_found/instance_not_active refusals) survive pause/rebind and are not retried as connection loss. A display projection failure is visible as binding_error while preserving the current surface, and a later priority replacement can still retire that surface. There is no local body-file corruption or journal-storage fallback path.

Network body/descriptor failures remain local `EntryState`/read errors. Explicit retry reuses descriptor location, `ContentAssembler` and record-version publication; an unavailable source does not clear accepted records or refresh the whole conversation. Media import/storage failures remain with the existing media owner and local body/media error surface. A rebuilt view can replay every retained body without network access, including after F5 or a Work switch in the same native App run. No cross-process body persistence is promised.

An explicit Work switch uses the existing cached binding and requests a Host refresh asynchronously. The initial cached content is assembled before one projection is published; intermediate cache batches are acknowledged without waiting for visible frames. The complete cached view is shown at the latest bottom without waiting for the Host refresh. The existing read/checkpoint path applies subsequent refreshed content, while same-Work refresh/F5, live streaming and reading protection keep their prior behavior. This does not add a display window, a second cache or another content-validation path.

Same-domain Extension bootstrap preserves its existing interaction object and local inputs. Obsolete controller release does not block installing a new binding or publishing conversation content. Local hydration errors remain local rather than invoking full observation recovery.

Earlier pages and completed bodies now belong to this holding point. The earlier action uses the current native earliest displayed entry ID directly; a descriptor scan cursor never acts as the display boundary. A request limit of 50 is a target, not a rejection threshold for a complete tool group. The reader shares descriptor locations and in-flight work and runs two body/descriptor jobs per content domain. Without actual visibility interest it does not scan all incomplete members. Visible incomplete records with non-image content (or descriptor-proven missing blocks/omitted text) still receive full bodies automatically; image-only records, including empty tool-result identity blocks, use the media owner instead. Explicit entry retry forces the full reader. Same-token checkpoints retain current interest; genuine replacement retires it. Whole-record contentComplete cannot prove mixed-record text completeness, so a necessary mixed image/text full read still includes the existing V2 image segments. No opaque cursor is interpreted to skip them. Already admitted requests may finish after leaving interest. Image-API cache-hit counts alone do not measure these observation/body requests. Native observation pause/Work switching stops queueing background bodies for the old view; in-flight bodies may finish into that Work's retained cache. A view/IPC waiter disappearing does not cancel an admitted earlier-page or coverage read. Successful completion clears only its own page/coverage/descriptor error, not unrelated entry errors. It reuses `ContentAssembler`; a stale continuation or descriptor revision discards the failed location and re-locates locally once, then offers a local retry if it still fails. App's old compaction-summary read/merge bypass, front-end hydration queues and per-entry direct-read commands have been removed.

This is content retention for the lifetime of the native App, including view rebinding and switching Work. Viewport/DOM/focus belong to the existing viewport/composer. The viewport persists a DOM-free entry/text anchor and following intent through small, independent localStorage records in localState.ts, keyed by connection/Work and checked against actual Host epoch/Session. Stored reading positions are used only for the view's initial binding (such as F5). Switching between Works starts a new visit at the latest output, including A→B→A; the previous visit's position is not restored. Manual reading remains protected while staying in the same Work, including same-Work rebinding. Where restoration applies, progressive rebuilding restores once the entry exists; user input cancels stale restoration. Missing entries fall back to the current target end after the seed, without another content scan. Storage failure does not block editing or overwrite a valid saved position. This synchronous display-intent persistence avoids an IPC flush race at F5/pagehide; it is not a second native content owner or an additional cross-process recovery promise.

## Native files and media

`SessionContent` also holds `session_media.rs`: a verified file index, request-domain aliases and single-flight image reads. A native-resolved authority/Work/epoch/runtime/ref keys the request, not the byte lifetime. Files remain throughout the native App's lifetime; separately verified SHA/length/MIME can reuse the same bytes across later request domains. No opaque server ref is parsed or manufactured, and no projection prune deletes a downloaded file.

The existing `sessions.rs` image frame/length/SHA/closure validator now writes chunks into a provisional sink instead of reserving a full image Vec. The media owner flushes/syncs, validates the raster signature, atomically publishes via `fs_publish`, then inserts the handle. Failed/interrupted provisional writes are removed and cannot be cache hits. Three network/sink transfers may run at once; this bounds transfer work, **not** WebView decoded pixels or total disk storage. Ref images do not wait for record-body completeness. Already-inline legacy image bytes can also be validated and registered locally in this same index, using a local digest alias rather than a fake server contentRef.

Tauri `attachment_preview` and `conversation_image` return `{handle,mimeType,sizeBytes,sha256}` (no binary channel); standard image.fileId reaches the latter through the existing local call. SessionContent checks the native accepted Work/epoch/runtime, takes its owning Machine from the actual read, and combines that with the native-resolved stable connection authority (including local endpoint) to find a verified receipt. That authority is not the observation request key. Matching receipts publish ready state into the existing image flight without waiting behind its network transfer; unassociated or MIME-different images keep the normal reader. A weak source index coalesces identical private files without retaining abandoned imports. `inline_conversation_image` registers already-local inline data. `aludock-media` resolves only registered opaque handles, never paths. Vue gets `convertFileSrc(handle, 'aludock-media')`; the URI response bypasses JSON/binary IPC and the Vue Uint8Array/Blob copies. Tauri's URI responder still reads a full file into its response Vec; this remaining display copy and WebView decoding have **not** been given a measured whole-App budget. `ConversationImage` observes proximity only for the first load, then retains the loaded img in the current conversation DOM. Scrolling never swaps it for a placeholder or repeatedly remounts it; browser decoding/cache policy is not a second client-owned image eviction system. The viewport remains the sole scroll owner and does not write an unchanged anchor position. Published images also stream file.read pages into this RunCache and return a MediaHandle. Their digest is local: file.read supplies length/identity/continuation, not a remote SHA. The obsolete Blob collector and 128 MiB Blob accounting are removed. save_preview_image accepts an opaque handle/name, verifies a streamed local copy and uses the existing native dialog/staging/commit; it never fetches a media URL into JavaScript.

The subsequent content module uses this same media repository for inline images encountered during full-body completion; in-memory record versions carry verified local handles rather than retransmitting that base64 through the view bridge or inventing a server ref. Image metadata is aligned only across a complete image subsequence, not across preview text indices; an omitted attachment identity can also be recovered from a unique exact verified byte match. Existing ref descriptors remain usable before body completion. The previously introduced native-URL save regression is repaired with exact media connect-src entries and CORS only for the trusted App origins (plus the configured debug origin). The URI test and App save success/cancel/failure controls are focused boundary evidence, not real-WebView verification. Trusted files are retained for this run; transport/chunk and replay limits bound work, not whole-process RSS. Native URI Vec delivery and WebView pixels remain distinct costs. The Host/Worker large-image implementation follows the shared V2 contract; the client does not carry a fallback for an obsolete private-transport bug.

`composer.ts` owns compact/expanded draft access, selection/composition and one resize schedule. Only an explicit surface transition transfers focus; output recovery never disables or recreates the editor. All remote submit entrypoints share `canSubmit` (including Enter and expanded editor), while local/Stop commands keep their separate dispatch semantics. Both global capture and modal-ancestor bubble Escape respect composition before any modal teardown. The existing localState schema now stores opaque per-Work text and per-attachment editing revisions; editor-bearing capture flushes them before native dispatch. Target-only controls do not depend on that flush. The store keeps captured-submit revisions and coalesces draft persistence over 250 ms, with immediate lifecycle/selection/attachment/submit flushes (pagehide, visibility, native blur and unmount). Ordinary modals suspend Extension dialog focus without discarding the interaction; on close an active Extension dialog regains ownership instead of competing with the old modal trigger.

## Session replacement and compaction templates

`operations.rs` retains only this native App's in-flight operations and unconsumed results, including lost replies (`unknown`). Tauri's existing typed Work mutations register their operation ID, original target scope and optional editor capture before executing an owned future. Dropping the IPC waiter does not cancel the request. Session actions, send/catalog command, Queue, Stop/Abort/Reopen/Forget, model/thinking/tools/settings and Create/Adopt/System-default use the same registry, without a second method dispatcher or a Host ledger. There is no operation.get and no automatic replay. `pending_operations` rebinds a rebuilt WebView; `aludock://operation` delivers changes; `consume_operation` removes any finished result the client has shown, a lost reply included; it never removes one still in flight. A retained lost reply is never replayed.

Session receipts and replacement events commit the native content target independently of editor recognition. Vue switches visible content on the committed replacement, not after a new read or Extension release. Cancelled/failed/unknown results do not replace it. The original editor is consumed/restored only when its persisted revision still matches; missing proof retains it. Navigate `editorText` and Fork `selectedText` remain native unconsumed results when later editing prevents automatic replacement, with an explicit append action. Queue retrieval does not use this replacement/append decision: a successful result is one insertion into the current editor. Create/Adopt receipts can update the directory but never select a Work on behalf of a rebuilt/different view. Queue-restored image handles are scoped by Host epoch/runtime as well as the existing connection binding, so a new Session cannot submit an old Session's images.

Known failures without a visible handoff stay in the same native registry until the user acknowledges their scoped OperationResults entry. A send failure may use the existing inline composer handoff only after a rendered frame and a fresh check of Work/Session, view revision, window visibility and covering surfaces; switching away during that handoff retains the native result. Send failures delivered to another Work use the same deferred entry, never its current composer. The current Work has a collapsed result entry (also in expanded editing); creation/directory or removed-Work results live in the Work list with an entry count. Another Work/Host does not receive the error or lose selection. An open initiating control/directory panel keeps its own error UI instead of getting a second result surface; closing it leaves the retained entry available. Receiving a terminal result, F5, or refreshing data is not acknowledgement, and acknowledging never resubmits the operation.

Default compaction templates are programmable reads: public Rust core `CompactionPromptTemplatesResult` and `DockClient::compaction_prompts(instance_id)` use capability `session.compaction-prompts.v1` and unary query `session.compaction.prompts` with `{instanceId}`. The result contains exactly `system`, `summarize`, `update`, `turnPrefix`, with no snapshot. Tauri `compaction_prompts` returns the core type; TypeScript `compactionPrompts(SessionContext)` retains the normal target fence. Host/Worker and Pi SDK supply the native defaults; the UI never fabricates fallback instructions.

The compact pane reads lazily and fences late responses. Each complete template uses `MarkdownDocumentSurface` for read-only source/reading/copy; editable supplemental instructions remain separate. These defaults are not the current provider payload: conversation and previous summary are dynamic, and extensions may take over or cancel. Model/Thinking changes during compaction affect subsequent calls without cancelling or replaying the active compaction.

## New Work system selection

`NewWorkDialog` uses `system.catalog` for the selected Machine/cwd (including recent directories), but this optional feature is not a prerequisite for ordinary creation. A valid explicit directory default can proceed directly; otherwise the dialog keeps Host order and requires a choice, even when project SYSTEM exists. Preview uses `ResourceDocument` / `MarkdownDocumentSurface`; Dock JSON opens as original text and copies the untouched complete file. Rust core owns all Protocol requests; neither Vue nor Tauri reads these source paths locally.

A correlated `capability_missing` naming only `system.templates.v1`, before any catalog page and during the original directory-create intent, continues through the existing create path without a system override. Rust preserves that Host refusal instead of marking its address unavailable. A stale result, refresh, partial catalog, explicit choice, or other read failure cannot create implicitly. Unsupported/failed reads never display the successful-empty-list message; default resolution stays exclusively with the owning Host. See the four-combination contract in `docs/client-integration.md`.

The confirmation checkbox starts unchecked. `system.default.set` is a separate mutation before creation only when checked; save failure stays on selection, while successful save remains visible if creation fails. The selected opaque `workerConfig` and create operation survive trust continuation, without repeating a completed save. Directory/Machine/connection/close changes fence read results; a lost reply is reported like any failure and never replayed. Focused gates: `node tests/newWorkSystem.test.mjs` (real Vue events and TS IPC bridge, native boundary fixture), and `cargo build --locked -p aludock-client-core --example protocol_system && node tests/systemProtocol.test.mjs` (requires root TS build; isolated real Rust/Host/Worker with explicit worker environment, not the CLI/login-shell path).

The existing `protocol_system` Rust→Host→Worker gate also calls the public compaction template method after Work creation and compares all four complete SHA256 values against the independently observed controlled Pi SDK defaults. Run it only with the integrated backend build; the Client-only detached tree does not supply that backend.
