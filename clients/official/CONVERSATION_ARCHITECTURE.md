# Conversation UI ownership

The official client keeps one Protocol V2 conversation state and the existing projection/live reducer path.

- `src/lib/conversationContent.ts` owns the visible conversation content lifecycle: bootstrap publication, historical page loading and incomplete-entry hydration/invalidations, live delta folding, projection scheduling, and streaming markers. It projects history only at bootstrap/history changes, and feeds each visible Follow event once into `createLiveConversationProjector`. `projectConversation` uses that same algorithm for canonical replay; there is no approximate second renderer. Message/tool maps retain part identity, ownership, complete content and images across start/update/completion. The folded replay log is independent of frame-local events. Both accept real Pi cumulative `{text, content:[text]}` snapshots, retain metadata/omitted fields, and preserve completion/image boundaries. Contiguous same-target deltas and replaceable tool snapshots are coalesced before one canonical frame application; timestamp formatting is lazy with a reused formatter. Unowned tools have distinct stable staging groups; only tool calls establish formal ownership, and tool results/native or published images retain it. First deltas register streaming before their first paint. It never reads or writes the DOM. Historical loading keeps the last bootstrap record as its fixed upper boundary: newer Worker history pages are scanned past, not merged into the live conversation. Only the boundary and its predecessors may be added or hydrated; subsequent output remains owned by Follow. The scan uses one history revision and retains the boundary page's cursor for hydration.
- `src/lib/conversationViewport.ts` owns follow intent, actual-bottom geometry, row/text anchors, layout observation, and every application-authored conversation scroll write. Content and media owners call `layoutChanged()` rather than scrolling directly. `scrollToBottom()` is the explicit reliable end action.
- `src/components/ConversationView.vue` groups stable rows; `ConversationRow.vue` and `ConversationProcessPart.vue` own row/part rendering. Raw assistant text is assembled on request, and tool detail serialization happens only in its own expanded part. The view does not load, project, or scroll content.
- `src/App.vue` composes those owners with connection/follow control, bridge access, image resources, and the rest of the shell.
- `src/conversation.css` is the single stylesheet owner for conversation viewport, rows, process parts, inline conversation images, reading controls, and responsive conversation layout.

Before a live reply becomes completed Markdown, content requests a text-preserving snapshot from the viewport. The viewport uses a native caret/range and the same exact text occurrence within that part; unchanged nodes take the fast path. The projector reports existing affected part identities; tail appends and changes below the reading position bypass anchor capture. Existing anchor elements are restored directly; a replaced part is looked up by identity. Native image part IDs include their contentRef as well as occurrence context, so successive different images in the same tool content slot have distinct component and anchor identities. Settlement includes every currently streaming part that is about to change presentation, even when there are no tools. Text capture happens at presentation transition, not on every delta. If caret capture or exact matching is unavailable, restoration falls back to the part-level anchor rather than interpreting or rewriting message content. Automatic layout restoration never uses the explicit forced-end action, and a scroll event with no downward movement cannot resume near-bottom following.

Debug content/history from the methods returned by `useConversationContent`; debug reading/follow behavior from the methods returned by `useConversationViewport`. Browser preview uses the real `ConversationView` and viewport controller without a native bridge; temporary validation data can be supplied by a browser driver without adding production hooks.

## Recovery, editing and focus

Ordinary Follow is same-domain strictly increasing, not consecutive: Host-private controller events keep their journal numbers. Rust and the Vue reducer enforce that contract. Extension UI consumes the reducer-accepted stream synchronously and retains its own binding/cursor for resume; session replacement goes through recovery, not a second unused Extension replacement reducer.

`conversationRecovery.ts` gives bootstrap/resume one scoped in-flight owner. Obsolete-subscription signals join it; a new subscription's buffered boundary can request one subsequent recovery. Host/Work/view/runtime/focus changes supersede it. External detach explicitly invalidates the recovery owner even when network reselection keeps those identities unchanged; reattach's own internal detach preserves its owner. Late native cleanup cannot absorb or cancel the next recovery. The owner predicate is passed into reattach/resume and checked after awaited native work before any continuation or fallback; supersession is not treated as a recoverable transport failure. App fences publication after native Follow start, controller clear, viewport restoration and Extension bootstrap. The retired Follow handle stays detachable until native accepts its replacement; Windows-away and Android background routing retain their existing native lifecycle.

`composer.ts` owns compact/expanded draft access, selection/composition and one resize schedule. Only an explicit surface transition transfers focus; output recovery never disables or recreates the editor. All remote submit entrypoints share `canSubmit` (including Enter and expanded editor), while local/Stop commands keep their separate dispatch semantics. Both global capture and modal-ancestor bubble Escape respect composition before any modal teardown. The store keeps captured-submit revisions and coalesces draft persistence over 250 ms, with immediate lifecycle/selection/attachment/submit flushes (pagehide, visibility, native blur and unmount). Ordinary modals suspend Extension dialog focus without discarding the interaction; on close an active Extension dialog regains ownership instead of competing with the old modal trigger.

## Session replacement and compaction templates

New, Switch, Navigate, Fork, Clone and Reload accept their own returned runtime generation, including event-before-reply ordering. Actual target changes, unmount and later runtime results are rejected. Rejections retain the same captured scope: stale trust/errors cannot publish to the new target, and unknown outcomes are recorded by Host/Work in the app store even after the initiating dialog unmounts. Returning to that Work still requires explicit reconciliation, never silent replay. App-owned Compact records its captured Host/Work scope too. Confirmation refreshes the active target without clearing selection and requires a successful authoritative read; actual user selection changes still invalidate that confirmation. Navigate's `editorText` and Fork's `selectedText` retain their operation-specific restoration. Clone targets the selected existing node and creates a Session within the same Work, not another Work.

Default compaction templates are programmable reads: public Rust core `CompactionPromptTemplatesResult` and `DockClient::compaction_prompts(instance_id)` use capability `session.compaction-prompts.v1` and unary query `session.compaction.prompts` with `{instanceId}`. The result contains exactly `system`, `summarize`, `update`, `turnPrefix`, with no snapshot. Tauri `compaction_prompts` returns the core type; TypeScript `compactionPrompts(SessionContext)` retains the normal target fence. Host/Worker and Pi SDK supply the native defaults; the UI never fabricates fallback instructions.

The compact pane reads lazily and fences late responses. Each complete template uses `MarkdownDocumentSurface` for read-only source/reading/copy; editable supplemental instructions remain separate. These defaults are not the current provider payload: conversation and previous summary are dynamic, and extensions may take over or cancel. Model/Thinking changes during compaction affect subsequent calls without cancelling or replaying the active compaction.

Focused evidence: `appInteraction.test.mjs` (actual App handlers with deferred native boundaries, not a native experience simulation), `followContinuity.test.mjs`, `submitDraft.test.mjs`, `sessionReload.test.mjs`, `liveDeltaFold.test.ts`, `conversationHydration.test.ts`, `conversationPresentation.test.ts`, `conversationViewport.test.ts` and the closed-browser native-edge case in `newWorkSystem.test.mjs`. These protect event/data/focus ownership contracts, not real Windows/Android IME acceptance under the user's sustained reasoning/tool workload.

## New Work system selection

`NewWorkDialog` resolves the selected Machine/cwd (including recent directories) through `system.catalog` before creating Work. A valid explicit directory default can proceed directly; otherwise the dialog keeps Host order and requires a choice, even when project SYSTEM exists. Preview uses `ResourceDocument` / `MarkdownDocumentSurface`; Dock JSON opens as original text and copies the untouched complete file. Rust core owns all Protocol requests; neither Vue nor Tauri reads these source paths locally.

The confirmation checkbox starts unchecked. `system.default.set` is a separate mutation before creation only when checked; save failure stays on selection, while successful save remains visible if creation fails. The selected opaque `workerConfig` and create operation survive trust continuation, without repeating a completed save. Directory/Machine/connection/close changes fence read results; unknown mutation outcomes use the existing no-replay flow. Focused gates: `node tests/newWorkSystem.test.mjs` (real Vue events and TS IPC bridge, native boundary fixture), and `cargo build --locked -p aludock-client-core --example protocol_system && node tests/systemProtocol.test.mjs` (requires root TS build; isolated real Rust/Host/Worker with explicit worker environment, not the CLI/login-shell path).

The existing `protocol_system` Rust→Host→Worker gate also calls the public compaction template method after Work creation and compares all four complete SHA256 values against the independently observed controlled Pi SDK defaults. Run it only with the integrated backend build; the Client-only detached tree does not supply that backend.
