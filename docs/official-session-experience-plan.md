# 官方客户端会话页面：全局盘点与修复方案

基线：`ec9bdad`。工作分支：`fix/official-session-experience`。范围：#301、#302、命令入口 `/new` 的页面延迟，以及这些问题共同涉及的 Work 会话页面状态和流程。用户另授权随本轮优化附带一个小项：收窄 Dock 附件 skill 的触发描述，避免普通图文聊天无谓加载 skill。

本文是实施前盘点与设计方案，**不是已实现架构或已通过的产品验收**。产品依据是 [STORY](../STORY.md)、用户本轮决定及两卡验收；现状对照 [Conversation ownership](../clients/official/CONVERSATION_ARCHITECTURE.md)。

## 一、结论与已定边界

**问题不是缺一个刷新按钮，而是客户端没有把“用户当前在做什么”“远端现在能否读到”“哪些内容已经在本地”分开管理。** 后果有两个方向：普通断联清掉不该消失的页面；真正新建成功却继续显示已经失效的旧会话。历史与媒体又被绑在这套恢复流程上，局部失败会带来整页重读和重复下载。

这条共同设计问题已有源码和隔离复现支持。但不是所有症状只有一个原因：图片关联丢失、正文拼装丢身份、分页位置错误、整页等待等各有具体缺陷，必须修到所属模块。

用户已定：

- 以正常客户端体验为目标，必要时允许对 Work 会话界面做真正的模块化重构，去掉集中处理所有业务的大 controller；不以最少改动行数为目标。
- **默认沿用现有 Protocol V2。** 早期 Rails WebConsole 至今正常、官方客户端卡住时网页仍正常，是已有使用事实，不能让用户重新证明，也不能先归咎于协议或外网。
- 优先检查并修复 Rust 本地后端和 Vue 的实际使用方式；若确认 Worker 投影/读取算法有缺陷，修对应实现，不把它叫成协议设计问题。
- 图片分块可单独用证据评估和调整；不能用调大块或内存预算替代完整读取/缓存方案。
- 保留 Vue/Tauri、Rust core、Host/Worker 边界、现有完整内容投影、展示组件和视口锚点；不重写客户端框架，不另起本地服务，不建立第二套会话真相。
- 本次先完成全局盘点和方案。未改运行代码；未安装、发布、启动/停止 managed service，未调用真实模型。

不纳入本轮实施：Windows“能滚动/收消息但不能点击输入”的原生输入故障、通用诊断平台、其他客户端改造、整体视觉换肤。会话页面的焦点/编辑器卸载属于本轮；不能用它冒充已解释 Windows 原生故障。

## 二、从产品看，页面应该是什么样

### 2.1 页面是工作台，不是连接状态的全屏显示器

保留当前视觉与信息架构：顶栏身份和常用配置、Work 抽屉、中央会话、底部编辑器和连接灯。改的是它们什么时候变化，不是重新画一套皮肤。

- **顶栏**说明正在看哪个 Work、哪个 Session。不能标题已变成新 Session，正文还冒充是旧 Session。
- **会话区**呈现当前 Session 的已知内容；历史、某条正文、某张图片分别加载和重试。已有内容不因后台读取失败而消失。
- **编辑器**属于用户在当前 Work 的本地操作。断线可继续输入、选字、展开编辑、选择/预览本地附件；发送、上传和远端命令按各自条件处理。
- **底栏连接灯**长期存在。用户明确点名：**删除会话区黄色“连接已中断／正在重试／连接恢复失败”提示框及其全局重试按钮（`alu-recovery-notice`）**，不是换颜色、换文案、缩小，或换另一种全局提示。普通断联/恢复收敛到底栏，不叠加全页错误、恢复横幅、重新配对面板和抢焦点；必要的主动重连入口也放在连接状态处，不能借它无差别重建会话。
- **Work 抽屉**显示最后确认的目录及其新鲜程度。连接失败不等于“没有 Work”，运行状态未更新也不能假装实时。
- **明确影响某次操作**才在对应位置提示：消息未发出、发送结果待确认、图片缺少本地内容、历史暂时读不到。一次操作超过一秒要有反馈，但不以整页打断代替局部反馈。
- 首次打开且没有可用本地内容、确证的身份问题、Work 真正停止是独立页面/动作，不套到每次网络波动上。

“保留画面”不等于远端事实永远不变，也不等于无限保留解码内存。保存的是可确认的本地内容和用户进度；需要网络确认的事实明确保持待更新。

### 2.2 用户入口与应有结果

| 场景 | 立即可见结果 | 后台动作与失败边界 |
|---|---|---|
| 初次打开、尚未配对 | 连接入口 | 不伪造 Work 或内容 |
| 已配对、第一次读取且无本地内容 | 明确连接/读取进度；失败优先重连 | 不暗示已撤销授权，不把重配当默认恢复 |
| 已进入 Work，短断网/切网 | 当前消息、草稿、附件预览、选区、阅读位置不变；底栏显示未连接 | 暂停依赖网络的操作；自动恢复已有观察，不自动发送草稿 |
| 后台暂停观察、Windows X/托盘驻留 | 不结束 Work，不清本地内容；返回原位置 | 合法暂停与故障分开；恢复观察，不把后台当退出 |
| 手动刷新当前 Work/列表 | 现有工作台不消失；对应刷新动作有进度 | 成功更新相应事实，失败保留最后成功状态；不是重新选择 Host |
| 切到另一个 Work 再返回 | 显示目标 Work 已有本地内容和本地编辑状态；无缓存时显示目标的加载态 | 不能让前一个 Work 的消息顶着新标题；切走只解除显示绑定，不删可信内容 |
| 页面刷新 F5/WebView 重建 | 从仍存活的原生 App 恢复已读内容、图片和已保存进度 | 重建显示资源，再接续观察；不是清磁盘缓存 |
| `/new` 提交、结果未到 | 命令处显示进行中，避免重复提交 | 不提前假装成功；取消/失败保留原会话 |
| `/new` 已确认成功 | **立即移走旧 Session 消息，显示新 Session（通常为空白）** | 新 Session 的欢迎消息/新输出随后补入；不等整份历史、Follow 握手或 Extension 清理才换画面 |
| `/new` 回执丢失，或另一入口换 Session | 依据关联回执/权威替换事件改变内容归属；无法确认则显示待确认 | 不自动重放 new；替换事件与回执先后到达都只应用同一次转换 |
| Resume/Tree Navigate/Fork/Clone | 目标已确认后切换到对应会话/分支；正文未齐就显示目标加载态 | 不把另一分支的缓存拼入目标；按操作保留返回的编辑文本 |
| Reload 资源、压缩 | 更新相应运行/资源事实，仍属同一内容时尽量保持阅读 | runtime 变化不自动等同“这是一个空白 New”；编辑器现有操作专属规则单独处理 |
| 正常追加消息/工具结果 | 增量显示，用户在旧处阅读不被拉走 | 已持久旧记录不因尾部追加反复重读 |
| 点击加载更早 | 一次动作展示当前最早记录之前的完整语义组，或明确到底/失败 | 网络页的重叠处理留在读取层，不能让用户空点 |
| 某条正文慢、同页图片已完成 | 图片及时显示，其余局部等待 | 不等整页；当前可见内容优先，有界后台预读 |
| 发送图片 | 本地预览→上传→正式消息→历史恢复连续显示 | 同可信内容复用本地文件；模型变换后的不同图片不能误认原件 |
| 发送结果不明 | 保留原草稿/附件和原操作关联；本地继续编辑 | 核对原操作的已知证据，不悄悄重发；新编辑不被旧回执吞掉 |
| Work 确认停止、真实授权/身份异常 | 显示对应事实和动作，不继续冒充可操作 | Stop、网络不可达、证书不符分别处理；身份异常不能靠盲目重配绕过 |
| 真正退出/系统终止 App 进程 | 可结束本次缓存寿命 | 正常退出清理，异常残留下次启动清理；不是后台即删 |

上述表不是一个巨型页面枚举。连接、当前内容归属、本地编辑和远端操作是可以同时存在的不同事实，不能互相替代。

## 三、现在实际怎么做

### 3.1 三条恢复入口有三种页面语义

```text
普通 Follow 断开
  → quiet catalog refresh → 尝试续接 → 必要时整份 bootstrap
  → 通常保留旧画面

Android 切网/部分前台恢复
  → route reselect → detach → app.loadActive
  → bootstrap 失败：payload=null → selectedWork=null
  → 编辑器卸载；选择 watcher 连带清附件预览、图片、阅读状态

手动刷新/Work 抽屉刷新
  → app.load → activateConnection → clearHostProjection
  → 即使仍是同一 Host/Work，也先制造一次选择消失，再读取
```

源码：`src/stores/app.ts:75–143,280–297`；`src/App.vue:818–853,2784–2960,3156–3162,3266–3269`（本节相对路径均在 `clients/official/`）。

`selectedWorkId` 和按 Host/Work 保存的草稿并非一定被删了。问题是 getter 依赖本次 payload 中的 Work，远端读失败让本地工作台暂时失去身份。再次读取能找回草稿，不代表 IME、焦点、未完成上传和 DOM 锚点从未被打断。

### 3.1.1 黄色连接恢复框：出现时实际发生什么

定位：`App.vue:3536–3538` 的 `alu-recovery-notice`，`conversation.css:7–9` 的琥珀色样式。它是会话区顶部的sticky元素，有实际占位和下外边距，不是只改变底栏灯；也不是模态弹窗，模板没有主动抢焦点或直接禁用textarea。

本次用实际模板条件和App恢复handlers做受控复现（`/tmp/official-session-inventory/recovery-banner-probe.mjs`及同名log，无真实Host请求）：

1. 只要已有会话且Follow断开，就可能出现；首个断开事件只要带message，就立即写成“连接恢复失败”，并不表示已经完成过一次恢复尝试。
2. 自动恢复要先等 `refreshWorksQuietly()` 完成，才安排1.5秒后的续接。诊断挂住目录读取时，黄框已显示“恢复失败”，真正续接还没被安排；目录慢会挡在恢复前面。
3. 点击框内“重试”直接走 `loadSelectedConversation(id, true)`，不是只重连传输：重置历史补全、重新读取整份会话，成功路径还会重新启动Follow、清理/恢复Extension并重新发布正文。
4. 开始完整读取时先清error、设loading，模板条件随即不成立，**框和重试按钮一起消失**；读取失败又重新出现。因此普通点击路径不是一个稳定显示“恢复中”的按钮，而可能形成出现→点击后消失→失败再出现的循环。
5. 断开/完整重读期间普通发送被 `canSubmit` 禁用，输入框模板本身没有对应的disabled/readonly。本轮证明了发送门控与黄框反复显隐，不能声称黄框本身直接锁住输入；输入打断还须追踪Host失败卸载编辑器、Extension恢复和焦点链。

恢复框的占位及反复挂载可能影响会话布局；未量测真实设备滚动跳动幅度或IME表现。修复要删此全局打断，并收敛背后的恢复范围和输入生命周期，不能只用CSS藏框后宣称解决。首次无内容连接失败、明确受影响的单次操作仍有准确反馈。

### 3.2 `/new` 成功和旧消息退场不是同一动作

```text
SessionManager.createNew 得到未取消的成功结果
  → ControlCenter 转发 resync 并关闭面板
  → App.resyncSession 应用新 Work 快照、重置编辑状态
  → loadSelectedConversation(id, true)
  → performConversationLoad 保留旧 conversationState
  → 重新 read → 原生接受 Follow 启动 → Extension clear
  → publishConversationBootstrap，旧消息这时才退场
```

`preserveUntilSwap || Boolean(conversationState.value)` 把“有旧画面”当成保留理由，没有区分同一 Session 恢复与明确替换。`conversationSwitching` 只比较 Work ID，new 在同一 Work 内换 Session 不会显示切换提示。

定位：`SessionManager.vue:365–371`、`ControlCenter.vue:259–262`、`App.vue:432–434,3024–3085,3233–3245`。

**已存在的正确改进不能忽略：** 当前 bootstrap 发布已经位于完整 Follow connected 确认和新 Extension bootstrap 之前；原生 `start_conversation_follow` 本身启动异步任务，不等待网络握手。因此不能说所有延迟都在“等 Follow 握手”。本次证明的是成功之后仍额外依赖读取和清理才能切走旧内容，现场具体慢在哪一步尚未计时。

### 3.3 内容、补全、显示和媒体寿命混在一起

- `conversationContent.publish` 用新 bootstrap 整体替换旧 records；已补全内容和更早历史没有原生本地仓库承接。
- `loadRecentHistory` 保留 200 条 bootstrap，却从最近 50 条页之后继续；下一次按钮只去重，不保证取得真正更早内容。
- Rust `complete_conversation_entry` 为每条记录重新读所属历史页，再串行补完整正文；同一页的描述没有作为可复用读取事实保存。
- Vue 全页补全 FIFO 并发 2，完成记录等 `batch.remaining===0` 才发布；并发有界本身没错，错在优先级和整页显示屏障。
- 补全失败里的 `protocol_error` 会回调 App 的整份会话恢复；`invalid_cursor` 却保留坏位置反复重试。错误类别与恢复范围没有对应好。
- `projected → pruneImageResources` 让当前渲染结果决定缓存是否存活；切选择直接撤销 Blob 和上传预览。暂无接入会话的磁盘内容层。
- Rust image stream 已验证 SHA/长度，但当前积累整图 Vec 后经 Tauri 再分块交给 Vue；Vue 另持有 Blob、上传预览、内联 base64，128 MiB 只覆盖其中一部分。

定位：`conversationContent.ts:237–254,298–480`；`App.vue:2413–2567,3135–3153`；`crates/aludock-client-core/src/sessions.rs:708–828,1193–1304,1898–1938`；`src-tauri/src/lib.rs:2948–3045`。

### 3.4 有组件化，不等于职责已经解耦

已有 `ConversationView/Row/ProcessPart/Image`、唯一内容投影器、`conversationViewport`、`composer`、恢复 single-flight、Extension store、Rust route manager。它们是可保留的基础。

问题是 App 仍串联并拥有读取、恢复、选择、媒体、上传、各类命令和焦点清理；Rust core 多数暴露一次性网络操作，Tauri 又持有单个 FollowTask，而整套恢复决策仍在 Vue。不能只把 App 拆成数个文件，也不能把所有这些逻辑原封不动搬成一个巨型 Rust controller。

## 四、底层问题：共同设计与独立缺陷分开

| 问题 | 已有证据 | 应修归属 |
|---|---|---|
| 临时不可读被当成当前 Work 不存在 | 真实 store 失败后 selected=null，重连草稿恢复 | 选择/目录模型与读取状态分开；页面挂载条件调整 |
| 真正替换还走“保留旧页直到重读” | 实际 App handler 受控读取复现新标题/旧 records 同存 | 会话替换处理；不能只加一次 clearTimeout/refresh |
| 局部内容失败升级成整页恢复 | reload callback 直接进入 Follow/Extension 全流程 | 内容读取与会话观察拆职责，按实际影响恢复 |
| 本地内容寿命等于当前视图寿命 | reset/prune/publish 的直接调用关系 | Rust 本地内容仓库、Vue 显示资源分层 |
| 页面依赖一次性 IPC 结果，Rust 未形成会话读取服务 | 一条 incomplete entry 一次重读页，再正文循环 | Rust 保存描述、合并读取、调度和缓存 |
| 首次几次历史按钮无效果 | 既有真实 Vue 加载器日志 200→200→200→200→250 | 客户端分页入口选错/位置管理错误 |
| 完整工具语义组可能被误判为坏响应 | `sessions.rs:1444–1452` 对 `conversation.history` 返回的 entries 强制不超过50，而既有分页允许完整组超过目标limit；本次为源码确认，未动态复现 | Rust 不应把请求目标数当返回硬上限；现有 `session_history` 校验没有此50条限制 |
| 新追加使旧读取游标失效 | 真实 adapter 日志；revision 使用 leaf 与全部 entry IDs | Worker token/读取快照算法及客户端失效处理；不是新协议需求 |
| 上传预览到实时消息关联丢失 | 既有真实事件转换：同图同 ref，live 无 fileId、history 有 | Worker 私有投影丢匹配信息；客户端可信别名交接 |
| 正文补全又抹掉 contentRef/fileId | Rust assembler 明确填 None、替换 content | Rust 完整性合并，不另造图片身份 |
| read 历史图片描述缺失、所有记录一律 incomplete | adapter 源码及 2 MiB 图日志 | Worker 投影准确性；已有 DTO 足够表达 |
| 图片慢不只是下载慢 | 2 MiB 原图走 88 次正文请求；快图等无关慢记录 | Rust 选读取路径、调度；Vue 及时发布 |
| 普通故障被引向重配 | native host_info 错误折叠、Vue按不可达显示重配问句 | Rust/Tauri错误分类、页面恢复动作 |

另外两项已发现、需要在同一流程验证的风险：

1. 结果未知的通用确认保存了 operationId，但有些路径只要刷新成功就解除未知；“看到了当前状态”和“证明原操作的结果”不能混称。协议没有凭空可调用的 `operation.get`；不要因此发明新接口。消息沿已有 operationId、Queue/事件关联核对，其他操作按既有权威结果能证明到哪里就说明到哪里，不能确认的保持待确认，不自动重放。
2. 同一 interaction 的完整重读先 `extensionUi.clear()` 再 bootstrap，可能破坏已有同域请求保留逻辑及焦点。这里有源码风险，尚未复现真实输入丢失。修复要区分普通恢复与确实失效，不以禁用 Extension UI 规避。

## 五、现有协议能做什么：先用好，不先扩

### 5.1 更早历史已有正确入口

`Protocol V2 session.history {beforeEntryId, limit}` 直接从给定记录之前读取，Rust `DockClient::session_history` 已实现（`sessions.rs:573–596`），Host journal 按完整语义组分页（`src/core/instance-event-journal.ts:127–141`）。Rails 的加载更早就是这条路径。

**建议分页优先复用这个入口和 bootstrap 已有的最早 entry 锚点。** `conversation.history` 留给所需正文的 descriptor 定位，不再用“最近 50 条扫描位置”替代“用户已显示历史的下界”。两者服务同一份 canonical records，不保存两套会话。

注意：Host `historyRevision` 和 Worker 正文 revision 是不同事实；不能忽略 revision，也不能把两个 scan 的实时边界随便拼起来。权威分支/边界需要更新时重新确认，缓存中的不可变内容继续保留；是否属于当前分支先确认再显示。切换分支、重启、压缩与正常追加的验证不能省略。

### 5.2 图片已有快路径，分块不能混为一谈

- `conversation.image` 已有单连接 ready/chunk/complete、512 KiB decoded chunk、SHA-256/长度验证及背压。
- 2 MiB 图的 **88 次请求**来自旧 `conversation.content` 的 32,000 base64 字符/次，不是 image stream 传了 88 个 TCP 包。
- 把已有 ref 的图片转到现有 image stream、消除重复读页、按可见内容调度、完成即发布，是优先项。
- 历史 read 图缺描述属于生产投影缺陷；补已有 image block，不必新增协议。旧 Host 只返回 inline 时完成必要的一次兼容读取，随后由 Rust 保留可信本地内容。
- 不能直接认定“将 32,000 调大就兼容”：现有 TypeScript parser 按该旧上限拒绝超大 chunk（`src/control/protocol.ts:1825–1870`）。若调参，须测旧消费方和真实 RTT 收益；用户已允许有证据的直接调整，但**本次未证明改变 image stream 块大小有收益，也未修改任何块大小**。

### 5.3 Rails 对照提供方向，不照搬另一套实现

本轮只读对照本地 `alubot_admin`：

- `conversation_surface.js:267–289` 用最早 entry 锚点翻页；
- `conversation_hydrator.js:1–88` 合并可见记录的正文请求；`conversation_record_content_reader.rb` 一次定位一批记录，而非每条重读同页；
- `alu_terminal_controller.js:263–286` 普通重读失败留住当前页面，而不是通过丢掉 instance 重新构造编辑器。

Rust 就是官方客户端本地后端，应承担对应读取服务职责；不需要把 Rails 搬进 App。Rails 也有旧正文分块和重建路径，不声称其所有情况无缺陷；未核对生产部署 commit 或重新实测速度。用户的实际体验对照不因此被否定。

兼容底线：新客户端能继续读旧 Host/长期 Worker，不能要求先停 Work 升级。优先客户端修复，产出端实现修正独立验证；旧源确实只能给旧分块时，明确首次读取限制，不伪称与新路径同速。持续追加打断旧正文这一尾项要先做有界实验，不能以无限重试或忽略 revision 糊过去；只有实际请求/响应反证才重新讨论协议。

## 六、怎么拆：按状态所有权，不按行数

以下是职责划分，模块名称是实施建议，不是要求新建这些同名类。每移交一项，同时删旧所有者的对应决策。

| 所有者 | 独占职责 | 不负责 |
|---|---|---|
| Rust 连接/路由模块（复用现有） | Host 身份、端点选择、传输错误类别、OS暂停信号 | 不因无法连接推断 Work结束，不操作编辑器 |
| Rust 会话观察/恢复模块 | 已接受 Work/Session 归属、观察位置、续接或重新确认、替换回执与事件归并 | 不做 DOM投影、滚动、焦点；不等媒体齐了才宣布替换 |
| Rust 本地操作关联模块 | 本次App内已发出操作的ID、原目标/内容域、pending/unknown与已确认结果；WebView重建后仍可认领 | 不复制Host操作账本，不自动重放，不新增远端查询接口 |
| Rust 会话内容仓库与读取器 | 已读 canonical records、正文描述/完整性、当前分支成员、历史上下界；相同读取共享、可见优先 | 不持有第二套 renderer，不用当前可见条目当存储保留清单 |
| Rust 媒体仓库 | 来源隔离、可信别名、验证/原子落盘、磁盘命中、失败临时文件、App生命周期 | 不按选中 Work或页面刷新清磁盘，不管理 Blob/解码 |
| Vue Work页面组合层 | 选择目标、绑定原生读模型、组合各 surface、派生信息优先级 | 不自己编排网络恢复、历史定位、全图下载；不维护另一份远端事实 |
| 现有 Vue 内容投影与展示组件 | canonical records/events → 唯一可见投影；按帧/小批更新 | 不用局部错误触发整页 bootstrap，不等待整页补全 |
| Vue 媒体显示模块 | 当前可见图片URL/解码资源、局部显示状态、向原生请求可见需求 | 释放显示资源不等于删除内容；不猜 fileId/ref/digest |
| 现有 composer/视口/焦点模块 | 本地编辑版本、composition/选区、显式焦点转移；阅读锚点/是否跟随 | 不因输出或网络恢复重新挂载、抢焦点 |
| Extension UI 模块 | 已确认交互与本地交互输入、操作权恢复 | 不阻塞普通会话切换；不把同一交互的重读当新提问 |

### 6.1 必须写清的几条接缝

1. **选择不等于一次成功请求。** 保留稳定 selected target 与最后成功快照；读取失败只更新 freshness/error。只有用户选择、确认停止/移除、权威替换等改变相应归属。Vue不按 payload 是否为空猜用户离开了 Work。
2. **当前显示归属与后台新数据绑定。** 任何更新带已确认来源/Work/Session及当前订阅归属；late response 可进入它所属的可信缓存，但不能更新已经切走的页面。连接选择代号只用来挡旧响应，不作为磁盘内容身份。
3. **替换先提交、补充随后到达。** new 成功回执或对应替换事实先完成本地目标切换、隔离旧任务/旧 Queue；再并行恢复所需观察和 Extension。事件先到、回执先到、用户已切其他 Work均有同一归并规则。取消/未知不构造成功空会话。内容归属已切换，不代表稍后回执携带的Navigate/Fork编辑文本可以被丢弃；编辑文本应用与内容切换分别按原操作和编辑版本归并，不重复清空用户后续输入。
4. **同会话恢复保内容，真正替换隔离内容。** 新 snapshot 的 active frames 仍按权威 read/checkpoint 边界接管；只复用已确认同一 immutable record 的完整内容，不靠文本指纹合并，不保留另一分支的 active output。
5. **本地内容不依赖 WebView存活。** 新增的会话正文/媒体仓库、索引和读取恢复事实都归 Rust core。缓存只要求本次原生App生命周期，优先采用原生内存索引加本次运行专属的磁盘目录，正文/媒体可按需读回；页面刷新接回同一仓库。正常退出或下次启动清理仅针对这份缓存，不碰用户原文件、主动保存的下载或Host附件。无需为本轮引入永久内容数据库、历史迁移或跨异常退出恢复工程。保留现有草稿按 Host/Work隔离、提交版本比较和生命周期 flush；不为了拆页面顺路重写全部本地设置 schema。
6. **一份媒体，多种引用。** 上传本地文件经 hash/大小核验，与成功附件receipt建立可信别名；live/history/ref指向相同经过验证的内容时复用。不同来源隔离，源图与变换图不同；opaque ref不能按字符串拆digest，文件名不能当关联。
7. **资源压力可见、可解释。** 热正文/显示资源可以有界，已读正文可落盘；媒体 provisional文件验证后原子提交。磁盘不足明确反馈，不悄悄反复淘汰已读图再下载。预算依据文件字节、base64副本、解码像素和原生峰值测量，不沿用未经测量的统一128 MiB。原生通过受限的本地内容句柄给显示层读图，不给WebView开放任意路径。
8. **保存已读内容不等于后台同步所有Work。** 观察仍按当前用户需求及已有平台后台策略进行，切走的Work只保留本地已知内容；不为所有缓存项长期建Follow，不新增通用同步引擎。当前没有证据要求重写虚拟列表或渲染器，先测实际占用，避免把范围扩大为整个UI技术栈重建。
9. **操作关联跨WebView存活。** 当前 `submitAttempts` 和 `unresolvedMutations` 仅在Vue内存，F5会丢失；它们必须收敛到原生本地操作关联模块，在发出请求前记录原operationId、Host/Work/Session域和原编辑版本，接收结果不依赖当前页面Promise。Vue重建只重新绑定，不重新提交。草稿格式可以保留，但需补可跨重建的编辑版本关联，不能凭文本相同认领或清草稿；无法证明未改动时保留草稿。只保留所需在途/未确认及尚未消费的结果，不建第二份永久操作日志。附件 `sourceToken` 仍不盲目持久化，由原生可信内容索引重新绑定。
10. **阅读进度也要有保存接缝。** 现有 `ConversationReadingAnchor` 含DOM对象，只能恢复同一surface；保留它处理当前页面布局变化，另由同一viewport模块导出可序列化的稳定record/part身份、相对偏移和跟随意图，按来源/Work/Session存入本次App的原生状态。返回/F5时先恢复所需缓存记录，再由Vue完成滚动，原生不碰DOM。图片/正文渐进到达继续沿该锚点；原记录不在目标分支时回退到目标内可确认的邻近记录，无匹配则使用目标默认位置，不能套旧Session坐标或反复重试定位。

### 6.2 要删/替换的旧耦合

- 同目标刷新中的 `clearHostProjection`；`loadActive` 失败清 payload；基于这类假选择变化的连带清理。
- 多套页面级重连 timer/恢复分支；原生成为观察恢复所有者后删旧流程，不常驻新旧双轨。
- `preserveUntilSwap` 一个布尔值承担所有恢复/替换语义；改为明确触发原因与更新范围。
- 当前投影直接决定媒体缓存寿命的 `projected → prune` 关系；显示资源释放仍保留在显示模块。
- 补全文失败直接召唤整页 Follow/Extension 恢复、每条补全重复定位整页、全页完成才显示的屏障。
- 普通断联的重复全局提示和错误重配引导；底栏脱离“编辑器必须可发送才存在”的挂载条件。

不删正确的迟到响应隔离、控制私有事件可跳号、语义组分页、原生错误校验、确定性 operation 关联、唯一投影和视口所有权。重构不是关闭这些能力换取表面稳定。

## 七、修复顺序：每步都走通一条完整用户流程

### A. 先落实页面状态边界，并一起修断联与 new

先用已知两种相反故障约束结构：选 Work→输入/阅读→断联→恢复，与同 Work `/new` 成功→立即切换。明确原生读模型及替换通知的接缝，拆页面组合、会话观察、编辑/焦点；同目标刷新不销毁画面，Session替换不等待补读。首步不先追求图片吞吐。

交付结果：普通连接失败不卸载编辑器；new成功后不留旧消息；失败/取消/未知不误清；旧响应和另一入口替换可正确归并。发送/new在途或结果未知后F5，原操作关联仍存在，迟到回执不吞新草稿。涉及 store、App/SessionManager、Rust/Tauri会话与操作关联接线、Extension同域恢复。不能只删除一个 `payload=null` 就宣布完成。

### B. Rust 接管已读内容与历史读取，Vue只投影

建立本次 App 生命周期的会话内容仓库，复用 `session_history(beforeEntryId)`；正文描述定位与媒体描述保存起来，合并相同任务，可见内容优先，完成即小批发布。修掉Rust把conversation history目标50条误作返回硬上限的接纳缺陷，保留完整工具语义组。局部失败只影响对应记录/分页；正常重连优先续接，确需权威重读时保留可验证缓存和锚点。

交付结果：200+记录首次点更早即前进；持续追加仍可读旧内容；切 Work和F5不把完整内容退回预览，并通过viewport可序列化进度接回旧阅读位置；快图不等慢正文。旧源的失效读取先定位再恢复，不反复发送坏游标。

### C. 媒体本地仓库接通发送与历史两端

改已有 image stream 接收为同一验证器管理的临时文件/提交结果，避免全图在 Rust/IPC/Vue反复复制；建立可信别名和下载合并。上传预览先注册本地内容；历史/实时都查同一内容；Vue只保留显示资源。真正退出清理，F5/切Work/托盘/后台不清理。

交付结果：真实选图/粘贴→预览→上传→直接发送或Queue→消息→刷新/切回连续显示；释放Blob后命中磁盘，不再次走Main/SubHost传图；磁盘满、下载中断、校验失败不产生有效缓存。

### D. 修已证实的产出端实现缺陷，守住兼容

修 live 投影附件关联、read历史图描述、准确完整性、append下读取位置寿命；不改既有公开协议形状。正文拼装同时保留已有metadata/身份。旧Host/旧长期Worker采用已有能力的客户端路径，不能以“升级后好了”替代普通阅读兼容验收。

交付结果：真实事件转换而非fixture预填fileId，旧/新入口均正确。图片块大小只有独立测量证明必要且兼容才调整，不作为本阶段前置条件。

### E. 联合原生验收与删旧路径

A–D按结果串行推进，可交错安排必要接线，但不长期保留两套所有者。最后统一清理被替代流程、更新架构文档并做 Android/Windows 实际使用验收。独立读取模块的局部通过不能代表整卡完成。

### F. 随本轮处理的小项：收窄附件 skill 触发描述

用户已确认此项加入优化需求，不是#301图片传输或#302连接恢复的根因，也不依赖大重构，可独立完成。

- **问题：** 仓库 `skills/dock-attachments/SKILL.md` 的 description 把“消息包含Dock附件元数据”当作触发条件。本次用户只发梗图，模型已经直接收到视觉输入，却仍先读了一次skill；没有取原文件的需要。
- **修改范围：** 修改仓库随包提供的skill描述，必要时使正文触发说明一致；不只改本机安装副本，不改Protocol V2、附件工具或图片视觉输入路径，不新增按扩展名/消息文本猜意图的代码。
- **目标描述：** 仅当任务需要获取附件原文件并进行文件级读取或处理时使用，例如解压ZIP、解析PDF、裁切图片、转换格式或校验文件。普通图文聊天、描述图片、讨论截图不触发；已作为视觉输入提供的图片，无需为了理解内容而取回原文件。由任务是否需要原文件决定，不由附件存在或文件类型单独决定。
- **保留能力：** 需要原文件时仍通过fileId解析；修改/转换前复制、保护原件、来源隔离及不可信内容规则保持不变。
- **验收：** “看看这个现象／聊这张图”直接理解回复，不仅因附件存在读取该skill或resolve；“处理ZIP/PDF／裁切素材并检查尺寸”能按需加载skill、正确取文件处理。核对实际随包skill的发现描述，不能只改正文而让旧description继续触发。已运行会话中的旧描述不算新版行为验证，按既有资源加载流程采用后再验收；不为本小项擅自安装、重启长期Work或调用真实模型。

这是用户点名的附加范围；目前只纳入计划，skill文件尚未修改。

### 最终验收硬标准：网络波动不应该打断输入框

这是用户明确追加的最终验收条件，不只是“草稿不丢”：

- 在当前Work/Session连续输入时，短断网、反复断开/恢复、Wi-Fi/移动网络切换、Host暂时不可达及随后的自动重连/后台重读，输入框始终可继续编辑。
- 不能因上述网络处理卸载、重建、隐藏、禁用输入框或设为只读；不能抢焦点、跳光标/选区、打断输入法正在组字，或让软键盘因客户端处理而收起。
- 底部输入框和展开编辑均适用。发送可以因网络暂时不可用，本地输入、修改、选字不能被连带锁住；恢复连接不自动发送草稿。
- Android/Windows实际界面验收：持续打字、中文组字/选字、选中文本修改时制造网络波动，检查断开、重试、重读和恢复全过程。不能用“重新点一下还能输入”或“重连后草稿恢复”判通过；未满足此项，不宣布本轮客户端体验修复完成。

## 九、投入与关键不确定项

这是跨 Vue/Rust 的有界模块重整，不是换框架，也不只是两三个补丁。估算按一个实施者连续工作计，包含删旧接线，以下范围不是排期承诺：

| 工作 | 实现投入 | 验证/文档投入 |
|---|---:|---:|
| A 页面与观察/替换职责、跨WebView操作关联、编辑/Extension连续性 | 8–12小时 | 4–6小时 |
| B 内容仓库、锚点分页与阅读进度接回、正文调度及渐进发布 | 11–18小时 | 5–7小时 |
| C 媒体磁盘/可信别名、上传到历史接通 | 10–16小时 | 4–7小时 |
| D 已证实产出端修正、兼容接线 | 4–8小时 | 3–5小时 |
| 联合原生回归、删旧与最终文档（避免重复计上述专项） | 2–4小时 | 4–7小时 |

合计：**实现约35–58小时，验证/文档约20–32小时**。独立设计审查补出了跨WebView的操作关联与阅读进度两项必要接线，已计入A/B；不是新增产品范围。设备、外网场景和用户验收的外部等待另计；本轮盘点30–50分钟的估算不代表实现也能在同一时长完成。

附加小项F预计实现5–10分钟、静态/随包描述核对约5分钟；实际图文与原文件处理行为在采用新版资源后验收，等待另计，不改变上述主体任务的量级。

先用A的完整流程和B/C的一条真实图片链校准投入，不先大面积改文件。主要不确定项：

- 旧长期Worker持续追加时，已有正文读取如何在不忽略身份/版本的前提下安全完成；先沿现有接口实验。
- Rust现有安全文件发布、附件暂存及workspace预览基础能复用多少；缓存寿命不能照搬workspace上下文清理。
- Android WebView重建/进程被系统终止，与原生App生命周期边界的实际触发。
- 大图解码、正文base64副本、原生接收缓冲各占多少资源；当前未测，不能先拍一个总预算。
- Extension同一交互在重连中的编辑/焦点连续性，以及未知操作的准确展示。

若必要投入接近阶段估算两倍、需要改变已定产品范围或有证据必须动协议，先收敛重复机制/复用，再报告具体漏项和剩余结果取得决定，不默默扩工程。
